# Задание: контейнеризация и развёртывание VPSHub

## Ситуация

Команда разработки передала работающий сервис каталога VPS и обработки заявок.
Ваша команда отвечает за воспроизводимый запуск, сеть, конфигурацию и сохранность данных.
Разрабатывать настоящий compute или менять бизнес-логику не требуется.

## Этап 1. Изучить приложение

1. Запустите проект локально по README.
2. Оформите и отмените заявку, зайдите менеджером.
3. Найдите точку входа, порт, переменные окружения и место хранения данных.
4. Нарисуйте путь запроса: браузер → приложение → БД.

Результат: краткое описание архитектуры и рабочий локальный запуск.

## Этап 2. Написать Dockerfile

- Выберите подходящий Python-образ.
- Установите зависимости отдельным слоем до копирования исходников.
- Добавьте `.dockerignore`: секреты, data, кэши, .venv и .git не должны попасть в образ.
- Запускайте приложение непривилегированным пользователем.
- Приложение слушает `0.0.0.0:8000`.
- Не используйте `--reload` и не зашивайте секреты в Dockerfile.
- Обеспечьте права пользователя на каталог данных, если используете SQLite.

Результат: образ собирается и запускается с настройками, переданными извне.

## Этап 3. Написать Docker Compose

Базовый вариант: приложение + SQLite с постоянным томом для `/app/data`
(либо другого каталога, выбранного в Dockerfile).
Полный вариант: приложение + PostgreSQL с отдельным именованным томом.

Для полного варианта:

- Имя сервиса БД, например `db`, используется в DATABASE_URL.
- БД доступна приложению внутри сети Compose; её порт не публикуется наружу.
- Настройки передаются из окружения или локального .env, который не коммитится.
- Настройте healthcheck PostgreSQL и ожидание готовности БД перед стартом приложения.
  Простого порядка запуска контейнеров недостаточно.
- Добавьте restart policy. Для healthcheck приложения можно использовать Python urllib,
  не предполагая, что curl уже установлен в slim-образе.
- Секреты приложения и PostgreSQL не следует передавать всем сервисам без необходимости.

Результат: проект запускается одной командой Compose, заявки переживают перезапуск
и пересоздание контейнеров. Удаление томов (`down -v`) уничтожает данные — это не
обычная команда остановки проекта.

## Этап 4. Развернуть на своей ВМ

1. Подготовьте Docker и Compose plugin.
2. Передайте исходники через Git или архив.
3. Создайте конфигурацию с собственными секретами.
4. Запустите сервисы, проверьте `/health` и `/ready`.
5. Настройте доступ и firewall: снаружи доступен только нужный веб-порт.
6. Оформите заявку из браузера на другом устройстве.
7. Перезапустите сервисы и докажите сохранность заявки.
8. Опишите команды запуска, просмотра логов, остановки и обновления в своём README.

Дополнительно: reverse proxy с HTTPS, `COOKIE_SECURE=true`, доменное имя,
ограничение частоты входа, резервное копирование и восстановление PostgreSQL.

## Критерии приёмки

| Критерий | Баллы |
| --- | ---: |
| Dockerfile: сборка, слои, запуск от обычного пользователя | 2 |
| Compose: приложение и PostgreSQL, внутренняя сеть | 2 |
| Конфигурация без секретов в репозитории и образе | 1 |
| Постоянный том и демонстрация сохранности данных | 2 |
| Работа на ВМ, диагностика health/ready и логов | 2 |
| README с воспроизводимым запуском | 1 |
| **Итого** | **10** |

За вариант только с SQLite — до 1 из 2 баллов за Compose; остальные критерии сохраняются.
Это рекомендуемая шкала для проекта, окончательные правила зачёта задаёт преподаватель.

## Что показать на защите

- Репозиторий с Dockerfile, Compose, .dockerignore и .env.example.
- Рабочий каталог и создание заявки через браузер.
- Панель менеджера и изменение статуса.
- Пересоздание контейнера с сохранённой заявкой.
- Почему `localhost` внутри контейнера приложения не указывает на контейнер БД.
- Где находятся данные и как выполнить резервное копирование.
- Как отличить недоступное приложение от недоступной БД.
